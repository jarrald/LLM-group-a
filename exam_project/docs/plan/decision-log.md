# StudyGraph — Decision Log

Lightweight ADRs. Every technical choice that constrains the code, the demo or the
evaluation gets an entry before (or with) the change. Statuses: **Proposed** (to be
confirmed by a spike or the group), **Accepted**, **Superseded**, **Rejected**.

Format: context → decision → consequences. Keep entries short; link to code or docs.

## ADR-001 — Python 3.12 managed by uv

- **Status:** Accepted (2026-10-30)
- **Context:** The machine default interpreter is 3.14.7. Several planned wheels
  (chromadb transitive dependencies such as `onnxruntime`, Streamlit dependencies) are not
  reliably published for a brand-new interpreter, and the repo-root `ruff` config targets
  an older version. `uv` is installed and already hosts a 3.12.12 interpreter.
- **Decision:** The project runs on Python 3.12 in an `uv`-managed `.venv`; all commands
  are `uv run ...`.
- **Consequences:** Reproducible installs and fewer wheel surprises; contributors must use
  `uv`, not the global interpreter. Version pins live in `pyproject.toml`/`uv.lock`.

## ADR-002 — Streamlit as the UI framework

- **Status:** Accepted
- **Context:** The MVP needs a chat UI, a Buddy form, a conversation list and visible
  retrieval sources. The team already works in Python; a JS build step adds cost the
  assignment does not reward.
- **Decision:** Streamlit with `st.navigation`/`st.Page` for four pages, using
  `st.chat_message` / `st.chat_input` / `st.write_stream`.
- **Consequences:** Very fast iteration and testable pages (`AppTest`); limited layout
  control and a per-rerun execution model, so all clients must live in `st.cache_resource`
  and state in `st.session_state`.

## ADR-003 — ChromaDB runs as a local server, not embedded

- **Status:** Accepted
- **Context:** Vector storage for course chunks. Chroma supports an embedded
  `PersistentClient` and a client-server mode. Separate inspection tools (ChromaUI,
  `chromadb-admin`, `chroma browse --local`) all attach to a **running server**, and a
  demonstrated RAG system is easier to inspect live.
- **Decision:** `chroma run --path .\data\chroma` on port 8000; the app uses
  `chromadb.HttpClient`. Tests use `EphemeralClient`. No `PersistentClient` on the same
  path while the server is running.
- **Consequences:** One extra process to start (documented in the README, and added to the
  demo script); a startup check with a clear error message when the server is down.

## ADR-004 — Embeddings are computed by us via Ollama

- **Status:** Accepted (embedding *model* still Proposed, ADR-007b)
- **Context:** Chroma's default embedding function downloads an ONNX MiniLM model, adds an
  `onnxruntime` dependency and fixes a 384-d default. The app already needs Ollama for
  generation, and the assignment values explainable local components.
- **Decision:** `app/adapters/embedder.py` calls `ollama.embed(...)` and passes vectors
  explicitly to `collection.add(embeddings=...)` and `collection.query(query_embeddings=...)`.
- **Consequences:** One local runtime, no extra Python dependency, dimension controlled by
  the chosen model; the embedding model name and dimension are stored in collection
  metadata and validated at startup (fail loudly on mismatch).

## ADR-005 — SQLite (stdlib) for application data

- **Status:** Accepted
- **Context:** Buddies, conversations, messages and snapshots must persist across restarts
  (NFR-06) with relationships and transactions. Options: JSON files, SQLite, an ORM, or
  reusing Chroma as a document store.
- **Decision:** SQLite via the standard library `sqlite3` behind repository classes; JSON
  column for the Buddy snapshot plus a `snapshot_version`; WAL mode and foreign keys on.
- **Consequences:** No new dependency, inspectable file, real constraints; schema changes
  need a small migration script. Chroma stays a pure vector store.

## ADR-006 — LangGraph orchestrates the chat turn (deliberately small)

- **Status:** Accepted
- **Context:** The turn has real branching: RAG vs non-RAG based on the snapshot, a
  retrieval-failure branch, and source propagation into persisted metadata. LangGraph is
  also a course topic worth demonstrating.
- **Decision:** One graph in `app/graph/`: `prepare → route → (retrieve) → build_prompt →
  generate → finalize`, typed `StudyGraphState`, pure routing functions, compiled once.
- **Consequences:** Branching is explicit and unit-testable, and a diagram can be shown in
  the synopsis; risk of over-engineering is handled by keeping nodes as thin wrappers over
  service functions and forbidding multi-agent topologies in the MVP.

## ADR-007 — Chat model: `llama3.2:3b`

- **Status:** Accepted (2026-10-30)
- **Context:** Answers must be generated by a locally running model. The machine has
  `llama3.2:3b`, `llama3.1:8b`, `qwen3.5:4b`, `qwen2.5-coder:7b` and others available.
  A demo must stay responsive on this hardware.
- **Decision:** `llama3.2:3b` (config `STUDYGRAPH_CHAT_MODEL`), `temperature = 0.2`,
  `num_ctx = 4096`. Measured with `uv run python .\scripts\smoke_llm.py`: **2.9 s** for a
  306-character answer (cold request). `llama3.1:8b` stays the fallback if answer quality
  proves insufficient for the evaluation.
- **Consequences:** Fast enough for live demos and for ~10 evaluation questions. Changing the
  model invalidates recorded evaluation results, so it must be re-run.

## ADR-007b — Embedding model: `nomic-embed-text` (768-d)

- **Status:** Accepted (2026-10-30)
- **Context:** Retrieval needs local embeddings with a stable dimension. Ollama already hosts
  the chat model, so a second runtime (torch/ONNX) is unnecessary.
- **Decision:** `nomic-embed-text`, dimension **768**, verified by an embed call
  (`scripts/smoke_llm.py`) and pinned in `STUDYGRAPH_EMBEDDING_DIM`. The dimension is also
  stored in the collection metadata and validated before every query.
- **Consequences:** Changing it requires `scripts/ingest.py --recreate` and a new collection
  version; batch embedding of 57 chunks took 0.9 s.

## ADR-008 — PDF → Markdown conversion tool

- **Status:** Proposed — to be closed by SG-010
- **Context:** Slides are PDFs; the RAG pipeline works on Markdown. Extraction quality
  drives everything downstream (chunking, metadata, answers). Candidates: `pypdf` (plain
  text, layout-poor), `pymupdf`/`pymupdf4llm` (layout-aware Markdown), heavier
  layout-model tools (slow, overkill for V1).
- **Decision (proposed):** Try a layout-aware PyMuPDF-based conversion first; fall back to
  `pypdf` if the output is unusable on the real slides.
- **Consequences:** Adds one dependency used only by the ingest scripts (not by the app at
  runtime). The chosen tool and its artefacts are recorded in the RAG doc.

## ADR-009 — Collection naming and index versioning

- **Status:** Accepted
- **Context:** Re-indexing must be safe, and an embedding-model change must not silently
  corrupt retrieval.
- **Decision:** One collection per course+version: `llms_for_devs_v1`. Collection metadata
  carries `embedding_model`, `embedding_dim`, `chunker_version`, `index_version`,
  `course_id`. Startup validates these against config and refuses to run on a mismatch with
  a "re-index required" message.
- **Consequences:** Safe incremental work; a renamed or re-embedded index means an explicit
  decision-log entry plus a documented re-index, not a silent overwrite.

## ADR-010 — Buddy snapshot format and versioning

- **Status:** Accepted
- **Context:** Existing conversations must not change when a Buddy is edited (FR-08,
  NFR-09), and must survive Buddy deletion.
- **Decision:** At conversation creation, serialise `{snapshot_version, buddy_id,
  buddy_name, target, tone, traits[], course_id}` to a JSON column on the conversation.
  Prompt construction reads the snapshot only. `snapshot_version` allows future migration.
- **Consequences:** Conversations are self-contained and reproducible for the RAG
  comparison; duplicated data by design. Renaming a Buddy does not rename old conversations.

## ADR-011 — ChromaUI is developer tooling, never a runtime dependency

- **Status:** Accepted
- **Context:** Browsing chunks visually is valuable for development and for the demo
  ("show me what was retrieved"). ChromaUI (Riko136/ChromaUI) is a small third-party
  Node ≥ 20 app on port 3000; `chromadb-admin` (`:3434`) and the official
  `chroma browse <collection> --local` are alternatives.
- **Decision:** Use ChromaUI for inspection/demo when available; document
  `chroma browse --local` as the zero-dependency fallback. The delivered app must never
  require it.
- **Consequences:** No risk to the MVP from third-party tool churn; the README marks it
  clearly as optional.

## ADR-012 — Tasks are data, not code paths

- **Status:** Accepted
- **Context:** Task is one of the 4T's and changes per interaction, while the Buddy stays
  fixed (design §4, FR-09).
- **Decision:** Task presets (explain, summarise, quiz, compare, review) live in a data
  structure with instruction text; the prompt builder injects the selected Task. Free-text
  input is allowed and treated as the Task too.
- **Consequences:** Adding a study activity needs no new branch in the graph; tests can
  assert Task text is present in the rendered prompt.

## ADR-013 — Course material lives under `docs/RAG/`, Markdown derivative committed

- **Status:** Accepted (2026-10-30)
- **Context:** Real material arrived: `docs/RAG/llm_for_developers/source/week1/` holds
  `Week1.pdf` (2.9 MB), the linear-regression notebook, `Salary_Data.csv`, two training-data
  text files and a PNG; `docs/RAG/llm_for_developers/week1/week1_complete_rag.md` is a 27 KB
  text-first transcription with `## N.` / `###` headings. The earlier plan assumed a
  `data/course_material/` layout that was never populated.
- **Decision:** the RAG input is `docs/RAG/llm_for_developers/week<N>/week<N>_complete_rag.md`.
  It is committed. The large binaries under `source/` (`*.pdf`, `*.png`) are git-ignored.
  The course files are not edited; chunk metadata is derived from the path and the first `#`
  heading (`doc_id = week-<N>`, `lecture = <N>`, `doc_name = first heading`).
- **Consequences:** the index can be rebuilt from the repository alone; no front-matter
  migration of existing material; later weeks follow the same convention. The conversion
  tool for future weeks remains ADR-008.

## ADR-014 — Regression-comparison dataset: `Salary_Data.csv`

- **Status:** Accepted (2026-10-30) — revisit only if it proves too small
- **Context:** The comparison exercise needs a single-input numerical prediction task with a
  train/reference split and held-out test inputs. The course material already ships
  `docs/RAG/llm_for_developers/source/week1/Salary_Data.csv` (30 rows,
  `YearsExperience → Salary`), used by `simple_linear_regression.ipynb` in the lecture.
- **Decision:** use that file for SG-080 … SG-084. Split the 30 rows into a reference portion
  and 1–3 held-out test rows; the RAG collection is built from the reference rows only.
- **Consequences:** the experiment uses the same data the course teaches with, so the
  comparison is easy to explain in the synopsis; the dataset is tiny, which must be stated as
  a limitation. No synthetic data has to be generated.

## ADR-015 — Chunking: heading-first, 900 / 120, deterministic ids

- **Status:** Accepted (2026-10-30)
- **Context:** The course Markdown is structured as `#` title, `## N. Section`, `### Subsection`
  with prose and bullets. Retrieval must return pieces a student can recognise, and
  re-indexing must not duplicate rows.
- **Decision:** split at every heading, repeat the heading in each chunk, group paragraphs
  into pieces of ≤ 900 characters with 120 characters of overlap, never split a fenced code
  block, drop stubs under 80 characters, and derive the id as
  `f"{doc_id}:{chunk_index:04d}:{sha1(text)[:12]}"` (`CHUNKER_VERSION = "1"`).
- **Consequences:** 57 chunks for Week 1, re-indexing is idempotent (57 → 57). Changing any
  parameter means a new chunker version and `ingest.py --recreate`.

## ADR-016 — A turn is persisted only after the answer succeeded

- **Status:** Accepted (2026-10-30)
- **Context:** If Ollama dies mid-turn, an earlier design would leave a stored user message
  with no answer, so a retry would send the same question twice.
- **Decision:** `ChatService.send_message` runs the graph first and writes the user and
  assistant messages afterwards. A failure therefore leaves the conversation untouched and
  the error surfaces to the caller (`LlmUnavailableError`).
- **Consequences:** Simple retry semantics and no half-turns; a very long generation keeps
  the previous state until it finishes. The UI must show the error and re-enable the input.

## ADR-017 — A Buddy carries three T's; Task belongs to the message

- **Status:** Accepted (2026-10-30) — team decision resolving design review D-01
- **Context:** The draw.io mocks put Task inside the Buddy ("ACTIVE CONFIGURATION … Tasks:
  Explain, Quiz"), while FR-09, `buddy-design.md` §3.1/§8 and the data model make Task a
  property of the interaction. Keeping Task on the Buddy would remove the "same Buddy,
  different Task" demonstration that the assignment grades.
- **Decision:** a Buddy stores **Traits, Tone, Target** and the optional course. Task is
  chosen in the chat, per message (`TaskSpec`), including a free-text option, and is
  recorded on the generated message together with `prompt_version`.
- **Consequences:** `BuddySnapshot` has no Task field; `FR-14` wording was corrected to
  match; the prompt builder is unchanged (it already took `TaskSpec` separately); the mocks'
  4-card "4 Ts" widget is superseded. Adding a *default* Task to a Buddy later would be a new
  ADR.

## ADR-018 — Three pages; conversation history lives inside Chat

- **Status:** Accepted (2026-10-30) — resolving design review D-03
- **Context:** `user-experience.md` §3 lists four areas (Chat, Buddy management, Buddy
  creation/editing, Conversation history); the mocks add Dashboard, Progress/Test Cards and
  Settings. The MVP needs a small, demonstrable surface.
- **Decision:** three Streamlit pages — **Chat**, **Buddies**, **About**. The conversation
  list, "new conversation" and the per-conversation mode badge live on the Chat page (in the
  sidebar), so Buddy creation/editing is one page and history is a section of Chat.
- **Consequences:** one navigation surface to test; Dashboard/Progress/Settings stay in
  `design.md` §8 as future work; `design-review.md` records the page-to-area mapping.

## ADR-019 — Additive column migrations, never rebuilds

- **Status:** Accepted (2026-10-30)
- **Context:** `messages.retrieval_top_k` was added after the first schema existed, and a
  local `data/studygraph.db` may already hold conversations.
- **Decision:** `SqliteStore.initialise()` reads `PRAGMA table_info` and issues an
  `ALTER TABLE … ADD COLUMN` for any column introduced later. Columns are only ever added,
  never dropped or retyped; a destructive change needs its own script and ADR.
- **Consequences:** upgrading an existing database needs nothing but a restart, and older
  rows read back with `None` for the new field. At this size a schema-history table is
  unnecessary.

## ADR-020 — Index every `week<N>/*.md`, not one fixed file per week

- **Status:** Accepted (2026-10-30) — supersedes the *layout* part of ADR-013
- **Context:** The course material was reorganised into
  `docs/RAG/llm_for_developers/llm_friendly/week<N>/`, and a week can hold several documents
  (week 3 has six: overview, ambiguity, gradient descent/embeddings, hallucinations, prompt
  injection, literature review). The previous loader expected exactly
  `week<N>/week<N>_complete_rag.md` one level below the root, so it found **nothing** and
  ingestion failed for anyone cloning the repository.
- **Decision:** discovery is recursive and layout-tolerant: every `*.md` below the configured
  root that sits inside a `week<N>` directory is a lecture document. Anything under a
  `source/` directory is ignored (raw PDFs/notebooks). `doc_id` is the file stem
  (`week3_hallucinations`), `lecture` comes from the directory, `doc_name` from the first `#`.
- **Consequences:** 8 documents → **153 chunks** (was 57 from week 1 alone). Adding a week is
  a file drop plus `ingest.py`. Chunk ids changed with the new `doc_id`, so the index was
  rebuilt with `--recreate`. The literature-review assignment file is indexed too — a
  conscious choice, reversible by curating the folder.
