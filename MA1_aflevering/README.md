# Local Multi-LLM Coding Workflow — Evaluation (Mandatory 1)

Two open-source, local, multi-endpoint LLM orchestration workflows that
collaboratively produce software artifacts (architecture, tickets, code, tests,
docs, deploy validation) for a small target project, plus the evaluation that
compares them and recommends one.

Everything runs against **two separate local Ollama endpoints** and routing is
**configuration-driven** (`config/endpoints.yaml`), never hard-coded.

| Endpoint | Base URL | Config key |
|---|---|---|
| Ollama server A | `http://localhost:11434` | `alpha` |
| Ollama server B | `http://localhost:11435` | `beta` |

## Roles → endpoints (default profile)

| Role | Endpoint | Model |
|---|---|---|
| architect | alpha (11434) | `architect:latest` |
| techlead  | alpha (11434) | `techlead:latest` |
| coder     | beta  (11435) | `coder:latest` |
| tester    | beta  (11435) | `tester:latest` |
| docs      | alpha (11434) | `docs:latest` |
| deploy    | beta  (11435) | `deploy:latest` |

The coding step runs **N > 2 parallel workers** (one per ticket) that round-robin
across both endpoints (`worker_pool` in the config).

Models are customizeable and found in /modelfiles, for our results we used:
- llama3.1:8b
- qwen2.5-coder:7b
- deepseek-coder:6.7b

All with a context of `8192` tokens.

## Quick start

> **Which Python environment?** The two candidates use **different** interpreters,
> and this is the most common trip-up:
>
> | Candidate | Runs on | Needs |
> |---|---|---|
> | **A — LangGraph** | your **system Python** | `pyyaml`, `langgraph`, `langchain-ollama`, `pytest` |
> | **B — CrewAI** | **`.venv-crewai` only** | `crewai`, `ollama`, `pytest` |
>
> Candidate A does **not** work inside `.venv-crewai` (that venv has no
> `langchain-core`). Run `deactivate` before any Candidate A command.

Prerequisites: Python 3.11+, and two Ollama servers with the role models
available (see `docs/setup-guide.md` for the full walkthrough).

```powershell
# ===== Candidate A — system Python (deactivate the crewai venv first) =====

# 1. Confirm both endpoints are up
curl.exe -s http://localhost:11434/api/tags
curl.exe -s http://localhost:11435/api/tags

# 2. Run the recommended workflow (Candidate A) end-to-end
python candidate_a_langgraph/orchestrator.py --run-id myrun --project demo_project

# 2b. Or run it in review mode: no project changes, just a diff to inspect
python candidate_a_langgraph/orchestrator.py --run-id myrun_review --control review

# 2c. Same workflow, different routing (proves config-driven switching)
python candidate_a_langgraph/orchestrator.py --config config/endpoints.alt.yaml --run-id myrun_alt

# 3. Inspect the generated artifacts and run their tests
Get-ChildItem demo_project -Recurse
python -m pytest demo_project -q
python demo_project/deploy/validate_deploy.py

# 3b. Run the workflow's own control/parser tests (no model calls needed)
python -m pytest candidate_a_langgraph/test_control.py -q   # -> 6 passed
```

Each run writes a self-contained folder under `runs/<run-id>/` containing the
staged artifacts, the raw model output per step, the unified diff against
`demo_project`, the test output, the deploy-validation output, the quality
report, and `run_manifest.json` (routing + per-call endpoint evidence).

## Candidate B (CrewAI)

```powershell
# isolated venv (CrewAI has many dependencies)
uv venv .venv-crewai --python 3.12
.venv-crewai\Scripts\Activate.ps1
uv pip install crewai ollama pytest

# native crew (use --no-memory, see caveats below)
python candidate_b_crewai/crew.py --config config/endpoints.crewai.yaml --run-id runB --no-memory

# the pre-native baseline crew, kept for the "before" comparison
python candidate_b_crewai/crew_naive.py --run-id runB_naive
```

Two caveats (full detail in `docs/synopsis.md` §4.2.1):

- **Use `--no-memory`.** Native `Crew(memory=True)` attaches *Search memory* /
  *Save to memory* tools to every agent, which Ollama rejects (HTTP 400) for any
  model without the `tools` capability — and it hung our full crew.
- **CrewAI's `output_file` writes the model output verbatim**, so generated `.py`
  files arrive wrapped in markdown fences and are not directly runnable without
  a de-fencing step.

`ollama` is needed for CrewAI's native Ollama embedder; `pytest` only for the
host-side evaluation harness.

## How the deliverables map to the brief

| Requirement | Where it is satisfied |
|---|---|
| 2 local endpoints, config routing | `config/endpoints.yaml`, `LLMClient` in `orchestrator.py` |
| Architecture (components, interfaces, topology, ADRs) | `architect` node → `demo_project/docs/architecture.md`, `docs/adr/`, `api/openapi.yaml` |
| Tech lead (tickets: scope, DoD, ordering) | `techlead` node → `runs/<id>/tickets.json` |
| Implementation (N>2 workers, multi-file) | `coders` node (parallel) → `demo_project/src/taskflow/*` |
| Testing & quality report | `tester` + `run_tests` + `quality` nodes → `reports/quality_report.md` |
| Documentation | `docs` node → `README.md`, `docs/api-usage.md`, `docs/runbook.md` |
| Deploy validation | `deploy` node → `Dockerfile`, `deploy/validate_deploy.py` (+ executed) |
| Predictability / control | `--control review` = plan + diff before applying |
| Reproducibility | per-run folders, `diff.patch`, git commit of `demo_project` |
| Context management | scoped prompts per role + `runs/<id>/context_manifest` + raw outputs |
| Security baseline | loopback-only endpoints, no public exposure |
